A database index is a data structure that improves the speed of read operations. It works in a similar way to an index in a book. Instead of scanning every row in a table, the database can use the index to locate relevant records more directly. Indexes are not free. They consume storage space and must be updated whenever data changes. That means a table with too many indexes may perform poorly during inserts and updates. The most common type is the B-tree index. Supports equality searches, range searches, and sorting. Hash indexes can be useful for exact matches, but they do not support ordered scans in the same way. Here's the thing — composite indexes include multiple columns and can serve queries that filter on several fields. Because the database can use a leading prefix more effectively than a non-leading column, also, the order of columns in a composite index matters. This detail is often overlooked during schema design. Query planners decide whether an index should be used. And really, even when an index exists, the planner may choose a full table scan if the query returns a large portion of the table. And this is not necessarily a mistake. Random access through an index can be slower than sequential reading when many rows are required. And yes, it should be noted that outdated statistics can lead to poor plans. So Databases need regular analysis of table distributions. Look, in addition, functions applied to indexed columns can prevent the index from being used unless an expression index exists. Indexes are an essential part of database performance, but they require careful planning. A useful approach is to measure slow queries, understand their access patterns, and add only the indexes that support those patterns. Moreover, each new index should be tested under realistic write load, because read improvements can be offset by slower writes. Ultimately, the goal is not to index every column. This goal is to create a small set of indexes that match the most important queries.
