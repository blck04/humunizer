A database index is a data structure that improves the speed of read operations. Also, it works in a similar way to an index in a book. Instead of scanning every row in a table, the database can use the index to locate relevant records more directly. Worth noting — indexes aren't free. They consume storage space and must be updated whenever data changes. Which means a table with too many indexes may perform poorly during inserts and updates. Also, the most common type is the B-tree index, which supports equality searches, range searches, and sorting. They don't support ordered scans in the same way. That said, hash indexes can be useful for exact matches. Composite indexes include multiple columns and can serve queries that filter on several fields. Also, the order of columns in a composite index matters because the database can use a leading prefix more effectively than a non-leading column. This detail is often overlooked during schema design. Query planners decide whether an index should be used. Here's the thing — even when an index exists, the planner may choose a full table scan if the query returns a large portion of the table. This isn't necessarily a mistake. And random access through an index can be slower than sequential reading when many rows are required. Outdated statistics can lead to poor plans. So Databases need regular analysis of table distributions. Also, functions applied to indexed columns can prevent the index from being used unless an expression index exists. They require careful planning. That said, indexes are an essential part of database performance. And yes, a useful approach is to measure slow queries, understand their access patterns. And Add only the indexes that support those patterns. Moreover, each new index should be tested under realistic write load, because read improvements can be offset by slower writes. Ultimately, the goal isn't to index every column. And the goal is to create a small set of indexes that match the most important queries.
